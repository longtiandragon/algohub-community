# 年级负责人（队长）功能设计

日期：2026-11-01。

状态：用户已确认设计并授权执行，功能已实现；实际使用和验证结果见 [年级负责人说明](../../cohort-leaders.md)。

代码依据：公开仓库 `main@9a4bb200e8fc488165e47ee850dcb7750c2237b7`。本地检出为 `6a4f865`，已比较两者，学校管理、学校授权和档案权限相关代码没有变化；远端新增了 V62 迁移。实施前应同步主分支并确认迁移编号。

关联功能建议：[Issue 草稿](../../issues/2026-11-01-cohort-leader-feature.md)。

## 1. 使用场景与本期范围

学校管理员希望把部分日常成员管理工作交给学生，例如由一名集训队负责人管理本校 2026 级学生。负责人需要审核入校申请、纠正班级和学号、查看学生学习档案，学校管理员仍负责全校和负责人任免。

本期仅做成员管理，不增加训练目标分配、提醒发送、训练活动发布、公告发布或独立集训队分组。

“年级”沿用现有 `school_member.enrollment_year`，表示入学年级，不表示毕业届次。界面使用“2026 级”，避免把“2026 届”解释成毕业年份。

负责人是学校内的委派身份，普通学生账号的 `app_user.role` 仍为 `STUDENT`。

## 2. 方案选择

采用独立的“学校＋管理年级＋负责人”授权记录，沿用现有 `school_administrator` 的授权思路。

相较于直接在 `school_member.member_role` 上添加队长标记，独立授权明确表达管理范围、授权人和撤销状态，不会把本人年级自动当成管理范围。无需改变平台角色枚举或 JWT 的全站角色解释。

任命时默认选择学生本人当前入学年级；管理年级由学校管理员明确指定，并独立保存。一届允许多名负责人；同一学生可被分别授权多个本校年级，每项授权单独撤销。未被明确授权的年级不因身份名称而开放。

## 3. 权限矩阵

| 操作 | 学校管理员 | 年级负责人 |
| --- | --- | --- |
| 任命、撤销负责人 | 自己负责的学校 | 不允许 |
| 查看和搜索成员 | 本校所有年级 | 授权年级 |
| 查看待审核、已通过、已拒绝记录 | 本校范围 | 授权年级 |
| 审核学生入校申请 | 本校范围 | 授权年级 |
| 修改班级、学号 | 本校范围 | 授权年级 |
| 修改成员学校、入学年级 | 按现有学校管理规则 | 不允许 |
| 查看学习档案的管理视角 | 本校已审核学生 | 授权年级已审核学生 |
| 修改学校管理员、平台管理员 | 保持现有规则 | 不允许 |
| 审核本人或调整负责人授权 | 任免通过负责人设置操作 | 不允许 |

平台管理员只有具有现有 `SCHOOLS` 权限时，才可通过同一授权入口管理负责人。不能利用旧的学校授权绕过受限平台管理员的权限。

队长不能通过拒绝另一名有效负责人的成员身份来间接撤销对方授权；此类成员状态调整交给学校管理员。修改同届其他负责人的普通班级、学号资料，仍按普通学生资料操作处理并记录审计。

以上是新增的管理权限，不收紧用户原有的正常浏览权。例如另一届学生的公开档案，仍可按普通登录用户规则浏览；负责人身份不提供该学生的私密档案访问权。

## 4. 授权与生命周期

### 4.1 任命资格

- 操作者是目标学校的有效学校管理员，或具备 `SCHOOLS` 权限的有效平台管理员。
- 被任命者是正常状态的普通学生，且已有该学校 `APPROVED` 成员记录和入学年级。
- 学校管理员不能任命自己，也不能将学校管理员、平台管理员作为队长候选人。
- 授权学校来自当前管理范围；管理年级为 2000～2100 的明确整数，必须属于当前开放年级或该学校已存在的成员年级。
- 重复授予同一有效范围是幂等操作，不产生重复授权。

### 4.2 每次请求的有效性

授权记录有效、操作者正常且仍为普通学生、其授权所依据的本校成员身份仍为 `APPROVED`，才可使用管理权限。学校管理员与平台管理员使用各自既有权限入口，不能借遗留队长授权绕过权限限制。不能仅依据前端角色、浏览器缓存或签发时的 JWT 内容判断。

队长的列表查询、计数、搜索和单条写入，都必须同时限制学校与管理年级。不能先取全校名单后交给前端过滤。

### 4.3 撤销与身份变化

- 学校管理员可立即撤销某一项授权，旧登录令牌不能继续使用。
- 被任命者离校、成员状态从已通过变为其他状态、成员所属学校或本人入学年级变化时，撤销其基于该成员身份获得的全部有效授权。
- 仅修改班级、学号不撤销负责人身份。
- 身份或年级恢复原值后，旧授权仍保持已撤销，必须由学校管理员重新任命。
- 账号被禁用时永久撤销旧授权；恢复账号状态不会恢复旧授权。
- 若负责人被任命为学校管理员，已有队长授权撤销，后续按学校管理员身份管理，避免降级后意外恢复旧授权。

对 `school_member` 的身份变更采用数据库触发器撤销关联授权，覆盖学校管理、本人资料修改、入校流程以及其他已有写入入口；对新增学校管理员授权的入口同步处理角色提升撤销。删除成员记录时关联授权随之删除，任免审计保留在既有审计体系中。

授权检查和写入在同一事务中完成，沿用已有授权共享锁、用户行锁的思路，固定加锁顺序。撤销操作完成后发起的新请求必须失败；此前已获得锁的在途操作允许先完成，撤销等待其结束。不得让失去执行资格的请求在撤销完成后继续写入。

## 5. 数据结构与迁移

新增 `school_cohort_leader` 表，字段职责如下：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | bigint，生成主键 | 单项授权编号 |
| school_id | bigint，关联 school | 授权学校 |
| enrollment_year | integer | 明确授权管理的入学年级 |
| user_id | bigint，关联 app_user | 被任命学生 |
| member_id | bigint，关联 school_member | 任命时依赖的本校已审核身份 |
| granted_by | bigint，关联 app_user | 授权人 |
| created_at | timestamptz | 授权时间 |
| revoked_at | timestamptz，可空 | 空表示尚未撤销 |
| revoked_by | bigint，可空 | 主动撤销操作者；自动撤销为空 |
| revoke_reason | varchar(64)，可空 | `MANUAL`、`MEMBERSHIP_CHANGED`、`PROMOTED_TO_SCHOOL_ADMIN`、`ROLE_CHANGED`、`ACCOUNT_DISABLED` |

约束和索引：

- `enrollment_year` 在 2000～2100 范围内。
- 对 `(school_id, enrollment_year, user_id)` 建立仅覆盖未撤销记录的唯一索引。
- 按 `user_id` 查询有效授权、按 `school_id` 查询负责人列表建立索引。
- `member_id` 关联记录删除时级联清理授权；应用层任命时校验成员、学校和用户一致。
- 学校删除保护包含新增授权表，不能因删除学校误清理授权关系。

迁移基于已检查的 V62 后追加 `V63__school_cohort_leaders.sql`；若合并前上游已占用编号，则顺延为下一个可用版本。不得修改已发布迁移。

已有用户不会自动获得负责人权限。回滚应用前先撤销新增负责人授权；数据库结构不通过重写 Flyway 历史回退。表和触发器的移除采用后续显式迁移，并单独确认授权、审计数据的保留。

## 6. 接口契约

### 6.1 学校管理员任免

| 方法与路径 | 输入 | 输出 / 行为 |
| --- | --- | --- |
| `GET /api/school-admin/{schoolId}/cohort-leaders/candidates` | `q`、`enrollmentYear`，可选 | 本校可任命学生，最多 30 人；包含用户 ID、显示名、本人年级 |
| `GET /api/school-admin/{schoolId}/cohort-leaders` | 可选 `enrollmentYear` | 当前有效授权，包含授权 ID、负责人、学校、管理年级、授权时间 |
| `POST /api/school-admin/{schoolId}/cohort-leaders` | `{userId, enrollmentYear}` | 返回授权记录；重复有效授权返回已有记录 |
| `DELETE /api/school-admin/{schoolId}/cohort-leaders/{grantId}` | 无请求体 | 撤销本校对应授权；重复撤销保持幂等 |

候选搜索和列表接口均先验证任命权限；负责人不能调用这些接口。接口响应不带邮箱、密码或平台凭据。

### 6.2 负责人工作区

| 方法与路径 | 输入 | 输出 / 行为 |
| --- | --- | --- |
| `GET /api/cohort-admin/scopes` | 无 | 当前有效范围：`schoolId`、`schoolName`、`enrollmentYear` |
| `GET /api/cohort-admin/{schoolId}/{year}/members` | `status`、`q`、`page` | `{rows, total}`，每页 50 条；条件只在该范围内生效 |
| `POST /api/cohort-admin/{schoolId}/{year}/members/{id}/review` | `{approve, reason}` | 更新本届允许管理的学生审核状态；拒绝原因最多 255 字 |
| `POST /api/cohort-admin/{schoolId}/{year}/members/{id}/profile` | `{className, studentNo}` | 仅更新班级和学号，保留原学校、入学年级及其他资料 |

资料更新请求拒绝学校、年级、用户 ID 等额外管理字段，返回参数错误；不能接受客户端先改年级再落入管理范围。班级最多 64 字，学号最多 32 字，空白值沿用现有归一化规则。

所有响应沿用 `ApiResult`。未登录返回 401，无范围授权返回 403，伪造或跨范围成员 ID 返回 404，输入非法返回 400。档案不可见继续使用现有统一 404 文案。

## 7. 学习档案访问

在 `AuthService.requireReadableProfile` 所用的管理读取判断中增加“有效年级授权＋目标本校已审核成员＋目标年级匹配”。目标必须为正常普通学生；新增的管理视角不能越过对学校管理员、平台管理员的保护。

个人档案、统计、热力图、已通过历史、Rating、成就、连续练习等已有读取入口共用这条范围判断，不能只保护页面入口而遗漏后端数据接口。

新增管理视角不等于全站管理员：邮箱、平台账号展示继续遵循已有隐私开关；不会额外开放平台凭据、登录会话、私人收藏笔记或管理接口。普通关注、好友消息继续走既有普通可见性判断，不能借学习档案的管理视角扩权。

访问非公开学习档案记录 `COHORT_PRIVATE_PROFILE_VIEW`，包含操作者、目标用户、学校与管理年级；不记录实际邮箱、学号、学习明细或凭据。

## 8. 前端流程

### 学校管理员

在学校管理页增加“年级负责人”管理区。选择学校后可查看各年级负责人，搜索本校已审核学生，确认管理年级后任命；每条授权支持撤销。跨学校切换时清空旧结果和编辑状态，过期请求不能覆盖当前学校结果。

### 年级负责人

用户信息增加 `managedCohorts`，元素为 `{schoolId, schoolName, enrollmentYear}`；前端增加 `isCohortLeader`。不改动 `isSchoolAdmin` 或全局角色判断。

侧栏和用户菜单增加“本届管理”，路由为 `/cohort-admin`。只有一个范围时直接进入；有多个范围时选择学校、年级。页面显示负责范围、成员搜索、审核状态、分页、资料编辑与学习档案链接。编辑窗口只出现班级和学号。

入口状态仅控制界面，所有请求仍由后端检查授权。授权失效后移除工作区旧数据、刷新本人信息并提示联系学校管理员，不能继续显示上一个授权范围的名单。负责人升为学校管理员后优先显示学校管理入口。

复用现有 `PageHeader`、`SectionCard`、`ResponsiveDialog` 等组件与学校成员列表表现，不加入独立样式系统或全站布局重构。

## 10. 验收与测试

### 后端范围测试

使用两所虚构学校 A、B，每校设置 2025、2026 级；准备学校管理员、两名 2026 级负责人、各年级学生、待审核成员及受限平台管理员。

1. A 校学校管理员任命 A 校已审核学生成功；同一授权重复提交只有一条有效记录。
2. 无法给 B 校学生、未审核学生、禁用用户或受保护管理员任命负责人。
3. A 校 2026 级负责人仅能获取对应名单，列表总数、搜索和分页不包含其他范围。
4. 可以审核本届普通待审核成员，不能审核本人、受保护管理员或通过拒绝另一名有效负责人间接撤权。
5. 只更新班级和学号；伪造学校、年级、成员 ID 不会越界。
6. 本届已审核普通学生的私密档案及相关统计读取有效；其他学校、未授权年级的私密档案均不可读。
7. 邮箱、平台账号、私人收藏、社交权限仍遵循原规则；其他年级公开档案的正常浏览不受影响。
8. 撤销后旧令牌失效；移校、本人年级变化、成员审核撤回、学校管理员身份提升均使旧授权失效。
9. 把年级或状态改回原值也不能恢复旧授权；仅改班级和学号不影响授权。
10. 既有学校管理员全校权限、受限平台管理员边界及全站管理员接口测试仍通过。
11. 并发撤销与成员写入按事务顺序完成，撤销完成后的新请求无写权限；授权检查不使用失效缓存。
12. 任免、审核、资料修改及非公开档案读取有可核验审计，且不记录敏感字段实际值。

建议新增 `CohortLeaderBoundaryTest`、`CohortLeaderLifecycleTest`，并扩展现有 `SchoolAdminBoundaryTest`、`PrivateReadPermissionBoundaryTest`、学校资源及删除保护测试。生命周期触发器必须在 PostgreSQL 测试，不能用 H2 或 SQLite 代替该验证。

### 前端回归

- 普通学生无入口；负责人入口显示准确；多个授权范围可切换。
- 任免候选、当前负责人列表及撤销结果在本校内刷新。
- 切换范围后的旧响应、旧错误、旧弹窗不会作用于新范围。
- 资料编辑只提交班级与学号；审核操作失败后保留当前列表并可重试。
- 授权失效后清空已有名单和弹窗，刷新身份信息。
- 桌面和手机均能完成任免、审核、编辑；截图使用虚构用户。

新增有针对性的页面脚本回归并接入现有 CI；沿用现有 Vue 组件编译和受控异步请求测试模式。

### 验证环境与结果声明

实施时使用 Java 21、Maven 3.9.13、Node.js 22.19.0、PostgreSQL 16、Redis 7，在独立 `_test` 数据库及 Redis 实例运行 `mvn -B verify`。前端运行 `type-check`、`build`、`test:browser-sync` 和全部受影响的页面回归。

本文中的验收条件由实现测试覆盖，实际运行结果单独记录在年级负责人说明中。实现已在独立本地测试环境验证，尚未向 GitHub 发布或部署。

## 11. PR 范围与实施顺序

先以关联 Issue 确认维护者接受“按年级委派”的方向，再提交同一功能 PR，按以下可审查顺序组织提交：

1. 授权模型、迁移、任免和生命周期测试。
2. 本届成员管理接口与跨学校、跨年级测试。
3. 统一学习档案范围判断与隐私回归。
4. 学校任免区、负责人工作区和前端回归。
5. 完整回归、使用文档、迁移与回滚说明。

不夹带旧问题修复、依赖升级、排行口径变更或生产部署。
